# AgriCast AI — Phase 1 Implementation Guide

## 1. Introduction

### What is Phase 1?

Phase 1 ("Foundation") builds every piece of infrastructure that every
future AgriCast AI feature will depend on: project scaffolding, the
frontend and backend architectures, the database connection, JWT-based
authentication, internationalization, the base UI shell, and the wiring
between frontend and backend. **No agriculture-specific feature (Weather,
AI Advisory, Sentinel/Satellite, Farms, Analytics, Reports, Notifications)
is implemented in this phase.**

### Why it exists

Real production SaaS products fail most often not because a feature was
missing, but because the foundation underneath the features was rushed:
inconsistent error handling, no validation, secrets committed to git, no
migration history, an auth system bolted on as an afterthought. Phase 1
exists to get all of that right *once*, so every later phase is "just" a
new module plugged into a pattern that already works.

### Expected outcome

By the end of Phase 1 you should be able to:

1. Clone the repo, install dependencies, and configure environment
   variables for both apps.
2. Create a PostgreSQL database and apply the Drizzle migration.
3. Register a new user and log in from the React frontend.
4. See a dashboard that proves the frontend is talking to the backend,
   which is talking to PostgreSQL.
5. Switch the UI language between English, Hindi, and Marathi.

### Why each folder exists

- **`config/`** — Anything that reads `process.env` or opens a resource
  (DB pool). Nothing outside `config/` should read `process.env` directly.
- **`db/schema/`** — One file per table. Keeps a 50-table database from
  becoming one unreadable file.
- **`db/migrations/`** — Auto-generated, checked into git. This is the
  database's version history — never hand-edit these files.
- **`modules/<name>/`** — One folder per feature/domain. Each module is
  self-contained: routes, controller, service, repository, validation.
  This is what "Feature Based Modular Monolith" means in practice.
- **`middlewares/`** — Cross-cutting Express concerns that aren't tied to
  one module.
- **`utils/`** — Small, stateless helpers used across modules.
- **Frontend `features/<name>/`** — Mirrors the backend: everything about
  a domain (its API calls, hooks, components) lives together instead of
  scattered across generic folders.
- **Frontend `layouts/`** — Each layout is a *shell*; pages plug into it via
  `<Outlet />`. Adding a new authenticated page never requires re-building
  the navbar/sidebar.

## 3. Tech Stack — why each piece was chosen

| Technology | Why |
|---|---|
| **React + Vite** | Fast dev server, native ES modules, minimal config compared to CRA. |
| **Tailwind CSS** | Utility-first styling keeps the design system centralized in tokens (see `index.css`) instead of scattered CSS files. |
| **React Router DOM** | Standard, well-documented client-side routing; nested routes map cleanly onto our layout system. |
| **Axios** | Interceptors let us attach JWTs and normalize errors in one place instead of every fetch call. |
| **TanStack Query** | Caching, retries, and loading/error state for server data without hand-rolled `useEffect` fetching. |
| **React Hook Form** | Uncontrolled-by-default forms are fast and keep validation logic declarative. |
| **React Toastify** | Simple, accessible toast notifications for success/error feedback. |
| **react-i18next** | The de facto standard for React i18n; supports lazy namespaces and persistence out of the box. |
| **React Leaflet / Chart.js** | Installed now (unused) because Phase 2+ (Sentinel maps, Analytics charts) will need them — avoids a mid-project dependency scramble. |
| **Express.js** | Minimal, unopinionated, huge ecosystem — the right choice for a modular monolith. |
| **PostgreSQL** | Relational integrity for farms/fields/users/subscriptions; strong geospatial support (PostGIS) for later phases. |
| **Drizzle ORM** | Type-safe, SQL-like query builder with first-class migration tooling, without a heavy runtime like some alternatives. |
| **JWT + bcrypt** | Stateless auth (no server-side session store needed yet) with industry-standard password hashing. |
| **Express Validator** | Declarative request validation that plugs directly into Express middleware. |
| **Helmet / CORS / Morgan** | Baseline security headers, explicit cross-origin policy, and HTTP access logging — non-negotiable for anything called "production-grade." |

## 7. Database Setup

### Create the database

Using `psql`:
```sql
CREATE USER agricast_user WITH PASSWORD 'agricast_password';
CREATE DATABASE agricast_ai OWNER agricast_user;
GRANT ALL PRIVILEGES ON DATABASE agricast_ai TO agricast_user;
```

Then set `backend/.env`:
```
DATABASE_URL=postgresql://agricast_user:agricast_password@localhost:5432/agricast_ai
```

### Configure Drizzle

Already configured in `backend/drizzle.config.js` — it reads
`DATABASE_URL` from `.env` and points at `src/db/schema/index.js` for the
schema and `src/db/migrations` for output. You don't need to edit it for
Phase 1.

### Run migrations

```bash
cd backend
npm run db:generate   # reads schema/*.js -> writes SQL into db/migrations
npm run db:migrate    # applies any not-yet-applied migration files
```

This was verified end-to-end while building this guide: `db:generate`
produced `0000_bored_christian_walker.sql` creating the `users` table, and
`db:migrate` applied it cleanly against a real PostgreSQL 16 instance.

### Seed the database

```bash
npm run db:seed
```

Creates one demo account if it doesn't already exist:
- Email: `demo@agricast.ai`
- Password: `Demo@12345`

## 8. Authentication Flow

### Diagram

```
┌─────────────┐        POST /auth/register            ┌─────────────┐
│             │  {fullName, email, password}           │             │
│   React     │ ──────────────────────────────────────►│   Express   │
│  Frontend   │                                         │   Backend   │
│             │ ◄────────────────────────────────────── │             │
└─────────────┘   { user, token }  (201 Created)        └──────┬──────┘
      │                                                        │
      │ store token in localStorage                           │ bcrypt.hash(password)
      │ (AuthContext + lib/axios tokenStorage)                 │ INSERT INTO users
      ▼                                                        ▼
┌─────────────┐        POST /auth/login                ┌─────────────┐
│   React     │  {email, password}                     │   Express   │
│  Frontend   │ ──────────────────────────────────────► │   Backend   │
│             │ ◄────────────────────────────────────── │             │
└─────────────┘   { user, token }  (200 OK)              └──────┬──────┘
      │                                                        │
      │ every subsequent request:                              │ bcrypt.compare()
      │ Authorization: Bearer <token>   ─────────────────────►  │ jwt.sign({sub, email})
      │                                                        ▼
      │                                            requireAuth middleware
      │                                            verifies JWT, sets req.user
      ▼
┌─────────────┐        GET /auth/me                     ┌─────────────┐
│   React     │ ──────────────────────────────────────► │   Express   │
│  Frontend   │ ◄────────────────────────────────────── │   Backend   │
└─────────────┘   { user }  (200 OK) or 401              └─────────────┘

Logout: frontend clears localStorage token and in-memory user state.
There is no server-side session to invalidate (JWTs are stateless) —
this is a deliberate Phase 1 tradeoff; a token-blocklist or short-lived
access + refresh token pair is a natural Phase 2+ hardening step.
```

### Register
1. `RegisterPage` collects fullName/email/password/confirmPassword via
   React Hook Form (client-side validation).
2. `AuthContext.register()` calls `authApi.register()`.
3. Backend: `auth.validation.js` re-validates server-side → `auth.service.js`
   checks for an existing email → hashes the password with bcrypt →
   `auth.repository.js` inserts the row → a JWT is signed and returned.
4. Frontend stores the token (`tokenStorage.set`) and the user in
   `AuthContext`, then redirects to `/dashboard`.

### Login
Same shape as register, but `auth.service.js` looks up the user by email
and compares the submitted password against `passwordHash` with
`bcrypt.compare`.

### JWT
- Signed with `HS256` using `JWT_SECRET` from the environment.
- Payload: `{ sub: userId, email }`.
- Expiry controlled by `JWT_EXPIRES_IN` (default `7d`).
- Verified on every protected request by `requireAuth` middleware, which
  reads the `Authorization: Bearer <token>` header.

### Logout
Client-side only in Phase 1: `AuthContext.logout()` clears the token from
`localStorage` and resets `user` to `null`.

## 9. Internationalization Flow

### Language selection
`LanguageSwitcher` renders a `<select>` bound to `i18n.resolvedLanguage`.
Changing it calls `i18n.changeLanguage(code)`, which react-i18next
propagates to every component using the `useTranslation()` hook —
no reload required.

### Translation files
Located at `frontend/src/i18n/locales/<lang>/translation.json`, one file
per supported language (`en`, `hi`, `mr`). Keys are namespaced by feature
(`auth.*`, `dashboard.*`, `nav.*`, etc.) so a translator can find every
string belonging to a screen in one place.

### Persistence
`i18next-browser-languagedetector` is configured (see
`frontend/src/i18n/index.js`) to check `localStorage` first
(`agricast_language` key) before falling back to the browser's `navigator`
language, and to cache whatever language ends up active back into
`localStorage`. This means a returning user's language choice survives a
page refresh or a new browser tab.

## 10. Project Rules

### Coding standards
- No business logic in controllers or React pages — controllers call
  services; pages call hooks/API layers.
- No direct database access outside a module's `*.repository.js`.
- No `process.env` access outside `config/env.js`.
- Every backend error is thrown as an `ApiError` (or a library error
  express-validator/etc. surfaces), never a bare `throw new Error()`.

### Naming conventions
- Backend files: `<name>.<layer>.js` (`auth.controller.js`,
  `auth.service.js`, `auth.repository.js`, `auth.validation.js`).
- React components: PascalCase file + export (`Navbar.jsx`,
  `DashboardPage.jsx`).
- React hooks/utilities: camelCase (`useAuth`, `tokenStorage`).
- Database columns: `snake_case` (Drizzle maps them to camelCase JS
  properties automatically, e.g. `full_name` ↔ `fullName`).

### Folder conventions
- Never merge two modules into one folder, even if small.
- Never rename the five backend layers (`routes / controller / service /
  repository / validation`) — later phases and any future contributor rely
  on the pattern being consistent.

### Git conventions
- Branch naming: `feature/<short-name>`, `fix/<short-name>`,
  `chore/<short-name>`.
- Never commit `.env` — only `.env.example`.

### Commit messages
Follow Conventional Commits:
```
feat(auth): add JWT-based login endpoint
fix(frontend): correct protected route redirect state
chore(db): add users migration
docs: update Phase1Guide with seed instructions
```

## 11. Error Handling Strategy

- **Backend**: every async controller is wrapped in `asyncHandler` so
  thrown/rejected errors flow to `errorMiddleware` automatically. Expected
  errors (`ApiError`) return their real status code and message; unexpected
  errors return a generic `500` with no stack trace in production
  (`NODE_ENV=production` hides `err.stack` from the response body).
- **Validation errors**: `express-validator` results are checked at the top
  of each controller action and converted into a single `400 ApiError`
  with a `details` array of per-field messages.
- **Frontend**: the shared Axios instance's response interceptor
  normalizes every error into `{ message }`, clears the stored token on any
  `401`, and each page/form catches errors locally to show inline messages
  or a toast — no unhandled promise rejections.

## 12. Security Checklist

- [x] Passwords hashed with bcrypt (`BCRYPT_SALT_ROUNDS`, default 12).
- [x] JWT secret loaded from environment, never hardcoded; app refuses to
      boot if `JWT_SECRET` or `DATABASE_URL` is missing.
- [x] `helmet()` sets standard security headers (verified: `X-Content-Type-
      Options`, `X-Frame-Options` present on responses).
- [x] `cors()` restricted to a single configured origin
      (`CORS_ORIGIN`), not `*`.
- [x] Request body size limited (`express.json({ limit: "10kb" })`) to
      reduce payload-based DoS risk.
- [x] All auth input validated server-side with `express-validator`
      (never trust client-side validation alone).
- [x] `.env` is gitignored; only `.env.example` (no real secrets) is
      committed.
- [x] Passwords and password hashes never appear in API responses
      (`sanitizeUser` strips `passwordHash` before sending the user object).
- [x] SQL injection is not possible through Drizzle's parameterized query
      builder (no raw string concatenation into SQL).
- [ ] Rate limiting on `/auth/login` and `/auth/register` — **not yet
      implemented**, recommended before real production traffic
      (e.g. `express-rate-limit`).
- [ ] Refresh-token rotation / token revocation — current JWTs are
      stateless and cannot be revoked before expiry; acceptable for Phase 1,
      revisit before handling sensitive farm/financial data.

## 15. Common Errors & Solutions

| Error | Cause | Fix |
|---|---|---|
| `[FATAL] Missing required environment variable: DATABASE_URL` | `.env` not created or missing a key | `cp .env.example .env` in `backend/` and fill in real values |
| `ECONNREFUSED` on server boot | PostgreSQL isn't running, or wrong host/port in `DATABASE_URL` | Start PostgreSQL (`pg_ctlcluster` / your OS service manager / pgAdmin) and confirm the port (default `5432`) |
| `password authentication failed for user "agricast_user"` | Wrong password in `DATABASE_URL`, or the role wasn't created | Re-run the `CREATE USER` SQL in Section 7, confirm the password matches `.env` |
| `relation "users" does not exist` | Migrations were never applied | Run `npm run db:migrate` from `backend/` |
| CORS error in the browser console | `CORS_ORIGIN` in backend `.env` doesn't match the frontend's actual URL | Set `CORS_ORIGIN=http://localhost:5173` (or wherever Vite is actually serving) |
| Frontend shows "Could not reach backend" on the dashboard | Backend isn't running, or `VITE_API_BASE_URL` points to the wrong port | Start the backend (`npm run dev` in `backend/`) and confirm `frontend/.env` matches its port |
| `JsonWebTokenError: invalid signature` | `JWT_SECRET` changed after tokens were issued (e.g. between environments) | Log in again to get a token signed with the current secret |
| `EADDRINUSE: address already in use :::5000` | Another process (often a previous `npm run dev`) is still bound to the port | Stop the other process, or change `PORT` in `backend/.env` |
| Tailwind classes not applying | Editor cache / Vite not picking up `@tailwindcss/vite` plugin | Restart `npm run dev`; confirm `vite.config.js` includes `tailwindcss()` in `plugins` |
